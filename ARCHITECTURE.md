# Architecture and MVP

## Product identity

The display name is **Pi desktop** and the repository name is `pi-agent-winui`. Installer downloads use `PiDesktop-Setup-<version>-x64.exe`. Existing C# namespaces, project filenames, executable/resource names, package GUIDs, the `PiAgentGui.Desktop` installer identity, credential keys, and `%LOCALAPPDATA%/PiAgentGui` storage remain stable for compatibility. The installer retains `%LOCALAPPDATA%/Programs/Pi Agent` and replaces the legacy Pi Agent shortcuts with Pi desktop shortcuts during installation.

- Confirmed model, effort and approval selector preferences are saved atomically beside each Pi session as `<session>.settings.json`, including before the first response when Pi has not yet flushed its JSONL. Reconnection restores approval first, then model and supported effort after extension initialization so profiles do not replace explicit selections. Pi still owns messages and runtime state. Conversation copies include confirmed preferences. Assistant copy, fork and clone buttons share the settled-response visibility rule.

- Provider onboarding stays hidden while initial credential discovery is pending. It appears only after a completed check confirms no configured provider, or a failed check supplies an error; startup uncertainty never displays a sign-in/setup prompt.

- The empty workspace is a project-focused landing surface: project name without its path, a prominent create-project/new-conversation action, contextual provider setup, and up to four recent unsettled conversations ordered by last use (creation time fallback). Recent rows reuse the existing conversation-selection command. Providers and Extensions remain accessible through compact footer actions. Native theme resources and a bounded scrolling single-column layout support both themes and narrow windows.

- Sending an ordinary idle-conversation prompt with confirmed missing provider configuration opens Providers and preserves the draft and screenshots. This uses the live onboarding inventory, not a credential-validity guess; unknown inventory does not block sending. Local composer commands remain available, and connecting never auto-sends the preserved prompt. The view-scoped navigation callback is detached when the conversation view unloads or switches owners.

- A getting-started card above Providers checks Pi's non-secret provider inventory on workspace startup. A successful inventory with no configured providers shows Connect provider, also near the composer and in the empty workspace; the collapsed sidebar has a setup indicator. API-key/environment configuration and OAuth both count. Failed/unknown inventory is displayed separately and does not assert that credentials are missing; configuration presence does not prove credentials are valid. Existing provider request errors remain responsible for expired/rejected credentials. Browsing and editing drafts remain available.
- Once a provider is configured, the card offers expandable optional extension recommendations using the existing catalog/setup dialogs and checks. The count says ready because an installed but incompatible/outdated extension may still require setup. It hides when all recommendations are ready or dismissed. Dismissal persists in `%LOCALAPPDATA%/PiAgentGui/onboarding.json` and never suppresses the missing-provider prompt. Extensions remain available from their normal page. Startup checks use provider metadata and local extension discovery, not model requests.

- Composer typing updates its draft immediately, but emits send/stop/steering action notifications only when their values change; it does not refresh unrelated queue properties per character. Suggestion updates are coalesced at low dispatcher priority so native text input takes priority. File suggestions reuse the current token search rather than cancelling/restarting for duplicate text/selection events. No debounce is applied to the actual draft or Send path.

- Completed change summaries offer Ask agent to revert. The clicked summary identifies its own original user message and final response, including restored historical cards. A bounded prompt includes those IDs, original request, captured tool evidence and patches, with explicit truncation notices. It asks the agent to inspect current files, preserve earlier/later work, avoid Git history/staging changes and external side-effect reversal, and explain unsafe reversals. This only prepares a normal editable composer draft; the user sends it through the usual model/permission flow. Existing drafts/attachments are preserved and active operations block preparation. No automatic filesystem rollback or RPC request occurs on click.

## Remote and WSL execution targets (2026-09-12)

- User decision: the local version on the desktop application's machine is authoritative when adding remote and WSL support. Remote targets must not silently replace local configuration or conversation state.
- Agreed product model: one logical project owns multiple named execution targets, each identifying Local Windows, a WSL distribution, or an SSH host and its own workspace folder. Each conversation persists its selected target; different targets do not require duplicate projects. New conversations default to the project's preferred target and can choose another. Concurrent conversations retain independent runtime ownership, including when using different targets.
- New project supports local-first, WSL-first, or remote-first creation, with either an existing folder or Clone Git repository (repository URL plus destination on the chosen target). A remote-first project needs no local checkout. Manage targets subsequently adds existing checkouts or clones on other targets. Pull remains an explicit update of an existing checkout, not an automatic project-creation side effect.
- Conversation headers and their file, Git, terminal and run surfaces follow the conversation's target. Separate checkouts do not automatically synchronize; Git push/pull transfers committed changes. Conversations using the same target folder share its working tree. Initially prefer New conversation on another target; any later target-switch feature must be explicit and idle-only because earlier history describes the previous environment.
- Sidebar requirement: each conversation item visibly identifies its execution target with a local/remote icon treatment; WSL must remain distinguishable through its target description and accessible label. A hovercard on the item opens after a slight intentional delay and shows the target name/type, machine or distribution, and workspace location. Consider associated PR information when available; the exact PR fields and delay remain design details to settle. Provide equivalent keyboard/focus access so target details are not hover-only. The icon identifies execution location, not connection health.
- Implemented initial support: keep Pi and its session files on Windows and delegate workspace tool operations to a selected WSL distribution or Linux SSH host through Pi's public extension operations. Pi continues to own transcript/runtime semantics; the desktop owns project associations and target selection. This avoids competing session replicas.
- Treat target identity and target-native workspace paths separately from the local Pi working/session directories. Workspace files live on the selected target; local authority does not imply automatic source-tree synchronization or overwriting remote files.
- Required scope includes target-aware agent tools, file browsing/editing, Git, terminals/scripts, project instructions, extension compatibility, cancellation and disconnect recovery. Never silently fall back to executing locally when a target is unavailable. Third-party extensions and MCP commands that perform their own I/O need explicit compatibility handling.
- Recommended sequence: shared execution-target boundary, WSL core tools, SSH core tools, then native-panel parity. Remote jobs continuing after desktop disconnection would require a separately designed supervisor/reconnection protocol; it is not supplied by Pi's stdin/stdout RPC alone.
- References: https://pi.dev/docs/latest/extensions#remote-execution ; https://pi.dev/docs/latest/rpc ; https://learn.microsoft.com/en-us/windows/wsl/basic-commands .

### Implemented boundaries and verification

- New conversations skip the target picker when the project has exactly one execution target. Multiple-target projects retain explicit selection and cancellation.
- SSH supports key/agent authentication or password authentication. Optional key path and auth mode are catalog metadata; secrets are not. Passwords/passphrases use Windows Credential Manager under `PiAgentGui.Ssh.<target-id>`. The shared workspace form uses PasswordBox, clears secrets when changing authentication mode/closing, and excludes transient secrets from serialization. Saved credentials can be updated in the target list.
- `SshLaunchOptions`/`TargetSshAuthentication` apply matching OpenSSH arguments across C# command runners, ConPTY terminals and Pi tools. `SSH_ASKPASS` invokes this executable's headless entry point, selected by a non-secret credential reference; `Program.Main` exits before WinUI initialization on that path. `SshCredentialSetup` resolves destination user/host with local `ssh -G` before saving the expected prompt. `SshAskpassPolicy` refuses unrelated prompts and host-trust confirmation. Strict host checking remains enabled, one password attempt is allowed, and keyboard-interactive/MFA/password-change workflows are not automated. Failed setup removes its newly saved credential; an uncertain catalog-write failure retains the credential to avoid breaking a potentially committed target. Native Windows credential storage and headless helper behavior are verified with unique temporary dummy entries; real SSH-host authentication remains a manual integration check. References: https://man.openbsd.org/ssh ; https://github.com/PowerShell/openssh-portable/blob/latestw_all/readpass.c .

- Target setup UI uses a shared `TargetWorkspaceForm` and `TargetLocationViewModel` for New project and Add execution target. Dialog content targets 560 effective pixels (648 maximum outer width), adapts to the window, scrolls vertically, and keeps actions in the native footer. Local/WSL/SSH and Existing folder/Clone repository are explicit native radio choices; only applicable fields are shown. Folder labels/placeholders follow the target and source choice; clone guidance says the exact new folder is used. Browse sits beside the local folder field and WSL refresh is an accessible adjacent icon.
- Execution targets opens on a saved-location list with name, type/host, folder and default marker. Add target switches to a separate form with Back; successful creation returns to the list. Existing conversation targets are unchanged. Sidebar tooltips retain native delayed activation and keyboard-accessible details, but now have a title, location icon/name/subtitle, monospace workspace path and a conditional separate PR section. Theme resources preserve light/dark/high-contrast behavior; absent PR status is not invented.

- WSL distribution discovery starts asynchronously at app launch and is cached in memory for that app lifetime. Both creation dialogs share the same cached task, so warm dialogs need no discovery process. The native dropdown selects the sole workspace distribution or WSL's default (first available if that default is unavailable). Docker's internal distributions are excluded. Refresh explicitly updates the shared cache; failed discovery and empty inventories show guidance. Inventory uses `wsl --list --quiet` and `--verbose`, never launches a Linux session, and never blocks application startup. See Microsoft's WSL command reference: https://learn.microsoft.com/windows/wsl/basic-commands .

- Catalog additions are `Project.Targets`, `Project.DefaultTargetId`, and `ConversationDraft.TargetId`. Legacy projects resolve an implicit local target whose ID equals the project ID; legacy conversations remain on that original target even after the default changes. The existing atomic catalog lock protects target updates. A target cannot be edited/removed or switched on an existing conversation in this version; adding targets and changing the new-conversation default are supported.
- New project and Execution targets support existing folders or an explicit Git clone into a new destination. Clone uses credentials already configured where Git runs, retains partial checkouts on failure, and never retries automatically. Target paths use their own OS dialect and POSIX comparison is case-sensitive.
- Remote Pi processes use a managed local runtime directory next to the local sessions, disable built-in tools and automatic third-party extensions/skills/templates, and explicitly load the bundled target extension plus the supported local Permission Modes integration. Connection requires the extension's matching target acknowledgement. No local tool fallback is enabled when extension loading or connectivity fails.
- `PiExtensions/execution-target.ts` registers target-native read/write/edit/bash/ls/find/grep and routes user bash commands. Reads/output are bounded; edits check the preimage hash; file replacement uses a target-side temporary sibling. Before each agent turn, bounded ancestor AGENTS.md, CLAUDE.md and AGENTS.override.md files are loaded from the target and appended to Pi's prompt; failure blocks workspace tools. The instruction inventory reports loaded local global context plus target files. Linux bash/coreutils/find/setsid are required; find/grep and filename references require ripgrep; Git operations require Git.
- Shell commands run through WSL or OpenSSH with a control-pipe watcher that terminates their process group on cancellation/disconnection. Explicitly detached descendants and uncertain transport failures still require user inspection; there is no persistent remote job supervisor, request replay, or automatic checkout synchronization. SSH uses config aliases, key/agent or password authentication, and strict known-host checking; configure custom ports outside the app.
- Sidebar rows display a location glyph with a native delayed tooltip containing target name/type/host/path and PR information when available. The context menu exposes Execution target details for keyboard access. Headers, terminals, run scripts and source control follow the selected conversation's target. Scripts and commit drafts are isolated by target; terminal sessions remain independent and labelled.
- Initial native parity limits: remote file browsing and text previews are read-only (edit through the agent or target terminal); tracked Git diffs and ordinary Git actions run remotely, but native conflict editing, untracked diff previews and Windows Recycle Bin actions remain local-only. GitHub PR discovery, Open in, process inspection, background research and third-party capability management remain local-only. Remote PR data is not fabricated. Remote hosts currently mean Linux with Bash, not Windows or macOS SSH hosts.
- Verification: ordinary Windows build, C# regression tests, pure TypeScript argument/path tests, and live Pi 0.85.1 tests against an isolated Ubuntu WSL temporary folder. Live checks exercise extension loading alongside Permission Modes 2.6.3, target instructions, read/write/edit/list/bash, stale-edit rejection and command cancellation without model requests. The GUI was not launched; actual SSH-host connectivity and manual native UI checks remain for the user. See `EXECUTION-TARGETS.md`.

## Local installer

Windows x64 distribution uses an unpackaged per-user Inno Setup installer. `Installer/Build-Installer.ps1` builds an untrimmed self-contained Release payload through `Properties/PublishProfiles/LocalInstaller.pubxml`. The stable install identity is `PiAgentGui.Desktop`, with files under `%LOCALAPPDATA%/Programs/Pi Agent`; user data stays separately under `%LOCALAPPDATA%/PiAgentGui` and Pi's own user directory. Increasing installer versions update in place; same-version repair and uninstall preserve user data, and downgrade is blocked. WebView2 is detected and bootstrapped only if absent. Generated assets stay under ignored `artifacts/installer`. This first local installer is unsigned and has no automatic update feed. See `Installer/README.md` for build, upgrade and verification details.

## Skills and optional MCP inventory

- MCP Add server defaults to a manual form (name, stdio command/one-argument-per-line/environment variables, or HTTP URL/headers), with JSON import as an alternate mode. NAME=value fields split on the first equals sign, preserving values; arguments retain spaces without shell tokenization. Hidden transport fields are omitted. Both modes use the same preview, validation, duplicate protection and global save service. Editing either form invalidates its previous preview.

- Skills has an Add globally dialog: choosing a local folder registers its absolute path in Pi's global `settings.json.skills` in place. All contents, including PowerShell scripts, are accepted unchanged; the GUI does not execute or filter them. Pi owns discovery and validation after restart. Package mode accepts one npm/Git source, previews the copyable `pi install` command, and requires an explicit Install globally click. Pi may install more than skills and run package installation scripts. The installer uses the located Pi executable/Node CLI directly with separate arguments, the global agent directory, a five-minute timeout and owned-process cancellation on dialog cancellation/app shutdown.
- MCP's Import JSON dialog accepts a file or pasted `mcpServers` JSON (up to 256 KB / 128 servers). It supports stdio command/args/env and HTTP URLs, preserving adapter-specific server options and credentials without executing anything during import. The supported global MCP Adapter is required. Preview allows selecting entries; names already present in the target config or current runtime are conflicts, regardless of the panel search filter. Only selected server definitions are merged into the agent directory's `mcp.json`; other top-level imported settings are ignored, existing destination fields are preserved. A late duplicate aborts the whole write. Import does not install executables, authenticate, or prove connectivity; restart Pi desktop to load the configuration.
- Global skill/MCP config updates use bounded reads, a cooperating-writer lock with a finite retry, optimistic external-change detection and atomic replacement. They preserve JSON values but normalize formatting/comments. These GUI services do not manage Pi's sessions or replace the MCP adapter's runtime. Other applications editing the same configuration should be closed while importing.

- The panel also includes Instructions for actual Pi-loaded global and project/ancestor context files. The bundled instructions.ts exposes an idle-only internal command using ctx.getSystemPromptOptions() and observes before_agent_start inputs. It sends only paths and SHA-256 content hashes through a reserved setStatus envelope; no context text is logged, persisted or injected by this integration. Unsupported Pi versions report unavailable rather than guessing loaded files. Snapshots clear on disconnect and remain conversation-specific.
- Clicking a loaded AGENTS.md, AGENTS.override.md or CLAUDE.md opens a full-height preview explicitly labeled as the saved disk file. Edit/Save/Cancel writes that exact file, preserving UTF-8 BOM and newline convention. Reads/writes are bounded to 256 KB; non-UTF-8, binary and linked files are not edited. Saves compare the original byte fingerprint and atomically replace from a sibling temporary file; in-app saves to a shared path are serialized. External changes detected before replacement require reopening the editor. This is optimistic concurrency, not an external-editor transaction lock. No files are created automatically and no active Pi runtime is restarted. Disk hashes differing from Pi's loaded hashes show reload required until that runtime actually reloads them. Refresh only inspects; restart Pi desktop to load saved changes. Parent-file edits affect all projects that inherit that file.

- The conversation header's More actions menu opens Instructions, skills & MCP in the existing resizable sidepanel. Skills come from that conversation's `get_commands` response (legacy path/location and newer sourceInfo supported), not a filesystem scan. Current upstream returns skills even when skill command suggestions are disabled. Clicking previews bounded Markdown; invocation remains in the composer command menu, with no Use button on list items. Paths are not displayed in the list. Tabs omit routine explanatory descriptions and show messages only for loading, empty, setup or unavailable states. Inventory reads can run during a turn and never reserve mutation state or send model requests.
- MCP remains opt-in through the independently maintained pi-mcp-adapter. The Extensions setup command pins published 2.33.0; existing older installations request an update. Installation is manual. The bundled `mcp-status.ts`, registered from write-diff.ts for main conversations only, observes `pi-mcp-adapter/status/v1` without importing the adapter. It forwards only names, states and counts through a reserved RPC setStatus key, outside the transcript and model context. It never connects, authenticates, discovers server configs, or executes MCP tools. Startup snapshots received before session_start are buffered.
- Native parsing validates snapshot version, state values and bounded payload sizes. Each conversation retains only its latest runtime snapshot, clears it on disconnect, and never persists it. The panel subscribes only to the selected conversation and rejects late inventory reads after selection changes. Cached/not-connected are normal lazy states, not failures. Missing/older adapter states link to setup; absence of a snapshot is never shown as successful connectivity. The first pass is read-only status, not server editing or authentication UI.
- Verified the published 2.33.0 status event contract and fake-runtime behavior. Live upgraded-adapter testing remains pending the user's manual installation. References: https://github.com/nicobailon/pi-mcp-adapter#runtime-status-snapshots and https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/rpc.md#commands.

## Markdown streaming crash diagnosis

- Conversation errors now use bounded presentation messages with common credential redaction, specific titles, and recovery guidance for authentication, limits, extension failures, storage, protocol faults, timeouts and exits. Both inline errors and disconnected recovery provide Details with a copyable report. Reports contain timestamp/reference, app/runtime/OS versions, exception types/HRESULTs, method-only stack frames, and Pi exit code where available; they exclude raw exception/provider messages, prompts, paths, and session identifiers. Existing reconnect behavior preserves drafts and never automatically resends requests, especially after acknowledgement timeouts.
- ProcessPiTransport drains stderr into an 8 KB in-memory tail only. On unexpected EOF it waits at most 200 ms for trailing stderr and reports a fixed dependency/access/memory hint plus exit code where available; raw stderr is not persisted or included in copied reports. CrashReportWriter uses the same metadata-only report format for last-ui-crash.txt. Error-dialog failures leave the app open rather than throwing another native callback exception.

The intermittent crash observed around automatic naming was traced with a full local dump to `MarkdownMessage.Render`: `String.Substring` received a Markdig block span outside the current streamed text. The exception escaped a `DispatcherQueueTimer` callback as native `0xc000027b` / `0x8000000B`, bypassing the application's managed unhandled-exception report. `MarkdownBlockSignature` validates span bounds and falls back to the complete text snapshot for invalid spans, preserving cache invalidation without unsafe slicing. Regression tests cover malformed spans and all streaming prefixes of representative Markdown. Ordinary Windows minidumps omitted the original exception's stack memory; a full dump plus SOS retained the managed exception stack.

## Terminal side panel

The TabView holds tab headers only; terminal surfaces live in a separate star-sized Grid below it. Keep each surface mounted while switching visibility between tabs. The TabView content presenter collapsed WebView2 to zero height even though scripts and shell output continued working. Live diagnostic measurements confirmed 400×0 before this separation and 400×653 afterward. Do not rely on a shell-output acknowledgement as proof that native layout is visible.

Builds use a concrete platform target and matching Windows runtime identifier, defaulting to x64 when an IDE selects AnyCPU. WebView2's WinRT native library otherwise defaults to x86 and can fail during environment creation with `0x8007007E` in a 64-bit process. Explicit x86 and ARM64 targets remain supported. Verify native dependencies in the ordinary build output, not only a separately configured verification build.

The conversation header toggles a right-side terminal panel with native TabView tabs. Tabs start in the selected project's working folder and retain that folder/session across conversation selection. Hiding preserves tabs; closing a tab ends its shell; closing the last tab closes the panel. The panel resizes with the native grip and overlays the conversation on narrow windows.

Services/Terminal owns Windows ConPTY handles, pipes, UTF-8 I/O, resize and shell lifetime. It starts PowerShell 7 from the standard installation when available, otherwise Windows PowerShell, only when a terminal tab is opened. Each tab owns one session. On app shutdown the renderer stops awaiting acknowledgements before ConPTY closes, allowing its final output to drain. ConPTY closes attached child processes. No Pi process or RPC state is reused for terminals.

The ANSI terminal surface uses bundled xterm.js 6.0.0 and fit-addon 0.11.0 in the existing WebView2 dependency. Native WinUI handles panel/tab chrome; this is a renderer, not a Node bridge. ## Agreed product model

- A project has a stable internal ID, a user-chosen display name, and a path to an existing local working directory.
- A project also has an extensible JSON object named `metadata`, defaulting to `{}`. Keep required domain fields typed rather than hiding them in metadata.
- Creating a project registers that directory in the application. It does not generate source code, initialize Git, or require a running Pi process.
- Projects contain conversations. Their stable IDs map to dedicated Pi session files independently of the selected sidebar item.
- Project metadata persists locally across application restarts.
- The application checks directory availability before starting Pi and shows a recoverable error if the directory is unavailable.
- The application owns project metadata and project-to-conversation associations. Pi owns session contents, model interaction, tool execution, context, and compaction.

## Implemented project persistence

- Storage: `%LOCALAPPDATA%\PiAgentGui\projects.json`, outside project working directories. `Configuration/ProjectStorageOptions.cs` provides the default and allows isolated test locations.
- One versioned JSON catalog stores project records with `id`, `name`, `path`, an inline `metadata` object, and typed `conversations` entries. There are no per-project metadata file references or database dependencies.
- Conversation drafts have a local `id`, `title`, and `createdAt`. They contain no messages or Pi runtime state. Existing version 1 catalogs without `conversations` load with an empty list; no migration is needed for this additive early-development field.
- JSON fits the initial small local catalog. `IProjectRepository` separates callers from the format so storage can change later if querying or scale warrants it.
- Metadata supports nested JSON values; unknown metadata keys round-trip unchanged. Metadata updates replace the complete object, so callers must merge existing keys when changing only part of it. Credentials must never be stored here.
- The catalog currently uses schema version 1. Unsupported versions, unknown structural fields, malformed JSON, invalid records, and duplicate records fail explicitly without replacing the original file. A missing catalog starts empty.
- Writes reread the catalog under an exclusive `.lock` file, serialize to a unique adjacent temporary file, and replace the catalog by a same-volume rename. Competing operations fail with an I/O error rather than overwriting each other; the UI should allow retry. The lock file remains on disk, but its OS lock is released when the operation ends.
- Names are trimmed. Paths must be absolute, are normalized with `Path.GetFullPath`, and lose unnecessary trailing separators. Duplicate normalized paths use case-insensitive comparison; duplicate IDs are rejected. Junctions, symlinks, and other filesystem aliases are not resolved for deduplication.
- Creation requires an existing accessible directory. Reading saved projects does not require their directories to remain available; unavailable projects remain visible for recovery.
- `App.xaml.cs` composes the repository, project service, shell view model, modal view model factory, and window-owned folder picker. The app remains unpackaged and uses per-user filesystem storage rather than package-identity APIs.
- `Tests/PiAgentGui.Tests.csproj` links the UI-independent production files so MSTest can exercise them without loading WinUI or adding a production assembly solely for testing.
- Verification commands: `dotnet test Tests/PiAgentGui.Tests.csproj --no-restore --verbosity minimal`; `dotnet build PiAgentGui.csproj --no-restore -p:Platform=x64 --verbosity minimal`. No GUI or Pi process has been launched during this implementation.

## Implemented Pi runtime and concurrency

- Before opening the project shell, `StartupViewModel` checks installation files asynchronously through `PiInstallationLocator`, also used by the process factory. - Listing projects creates lightweight workspace objects, not processes. First selecting a conversation connects it. Switching selection does not disconnect any conversation. Several conversations can stream simultaneously, including within one project; they share that project's working directory, not separate Git worktrees.
- Each connected conversation owns a separate hidden process and RPC client. There is no shared `switch_session` process. Internal disconnect closes only that process; window shutdown disposes every workspace concurrently. Cleanup closes stdin and uses bounded exit waits, terminating only the owned process tree when necessary.
- Connection management is an implementation detail: the normal interface has no Connect/Disconnect controls. The conversation area shows Loading conversation until startup and history are ready, then reveals the transcript and composer together. The sidebar and extension questions remain usable during startup. Already prepared conversations do not reload on selection; startup or runtime failures show a local recovery surface with Retry. Active turns stay in the chat view with status and Stop. Model dropdown work is explicitly deferred until the basic loop is complete.
- Session path: `%LOCALAPPDATA%\PiAgentGui\sessions\<projectId:N>\<conversationId:N>.jsonl`, derived by `PiSessionPaths`. Launch arguments pass `--mode rpc --session <absolute-file> --session-dir <parent>`, with the project's folder as the working directory. Pi creates and maintains the JSONL file; an empty conversation may have no session file until Pi persists its first assistant turn.
- The same path is reused after restart or reconnect. The catalog schema is unchanged; no session paths or messages are stored in arbitrary metadata. A lifetime `.jsonl.lock` file opened with `FileShare.None` prevents competing app windows from opening the same session. This is an application lock; external Pi invocations do not honor it automatically.
- Startup queries state and history, checks the returned session path, and displays Pi's active-context messages. `get_messages` is not a browser for pre-compaction history or abandoned branches. The GUI never edits Pi's session files.
- `PiProcessStartInfoFactory` resolves a native `pi.exe`, or the npm package's `dist/cli.js` with `node.exe`, from PATH and the usual per-user npm location. Absolute overrides: `PI_GUI_PI_EXECUTABLE` and `PI_GUI_NODE_EXECUTABLE`. Arguments use `ProcessStartInfo.ArgumentList`, never a shell command string. Setup instructions and official references are in `PI-SETUP.md`.
- Protocol framing splits only on LF, strips one trailing CR, and rejects incomplete/oversized records. Stderr is drained separately without persisting potentially sensitive content. RPC request IDs correlate replies; a single reader orders snapshots and events before UI dispatch.
- `PiTranscript` projects indexed text deltas and authoritative final messages. Accumulated tool output replaces the previous partial result. Tool arguments, results, and failures are visible; text is selectable. Basic Markdown and fenced code panels are rendered natively. Syntax highlighting, thinking blocks, and attachments remain outside this pass.

- Stop sends `clear_queue` then `abort` to the selected conversation only. Prompt rejection preserves the draft; uncertain acceptance never causes automatic replay. A successfully acknowledged prompt clears its submitted draft even if subsequent state reconciliation fails.

The sidebar shows running activity and pending-question/error indicators. The virtualized transcript follows the tail while the user is near the bottom.
